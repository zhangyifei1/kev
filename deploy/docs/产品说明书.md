# Kev-4B 产品说明书

> 内网部署版本,服务地址 `http://10.94.1.8:8009`(Docker 容器 `kev-4b`,固定 1 号 GPU 卡)
> 读者:产品、业务接入方、运营。技术细节见《技术文档》,字段级协议见《接口文档》,性能数据见《压测报告》。

## 一句话介绍

Kev-4B 是一个**决策判断服务**:给它一段背景材料(政策、合同、对话记录、评审规则……)和一批问题,它一次性返回所有问题的判断结果和置信度。它**不生成文本、不解释理由**,只输出结构化判断——因此非常快(单题毫秒级),也因此在产品上要把它当"打分器"用,而不是当"问答助手"用。

## 30 秒判断:我的需求适不适合用 Kev

| 你的需求 | 是否适合 | 说明 |
|---|---|---|
| "判断这件事是否违规/符合条件" | ✅ 非常适合 | noul 题型,毫秒级返回 |
| "把这些工单/评论/材料分到预设类别" | ✅ 非常适合 | choice 题型,一次请求可挂多题 |
| "按 1~5 级给方案/内容打分" | ✅ 非常适合 | score 题型 |
| "同一份材料要查很多个检查项" | ✅ 甜点场景 | 一次请求挂几十题,材料只编码一次 |
| "根据材料回答开放问题(为什么、怎么办)" | ❌ 不适合 | Kev 不生成文本 |
| "给出判断依据、引用原文条款" | ❌ 不适合 | 只给概率,不给理由 |
| "材料超过约 4~8 万汉字" | ❌ 超上限 | state 上限 65,536 token,超长 422 |

**一句话标准**:能把需求表达成"对照一段材料,做是非判断/多选一/分级打分",就能用 Kev;需要"写一段话出来"的需求,不能用。

## 适合的场景

| 场景 | 用法 | 问题类型 |
|---|---|---|
| 合规/政策检查 | 把制度条文放 state,问"这个操作是否违反政策" | noul(是/否) |
| 内容审核初筛 | 把待审内容放 state,按审核标准打分或分类 | score / choice |
| 工单/评论自动分类 | 把工单内容放 state,从预设类别里选 | choice(多选一) |
| 方案评审 | 把评审标准放 state,对每个候选方案打分 | score(1~5 级) |
| 质量抽检 | 把质检规则放 state,对样本逐条判断 | noul / choice |
| 大批量材料预审 | 每份材料一个 state,挂几十个检查项一次问完 | 混合,一次请求不限题数 |

**不适合的场景**:开放问答(它会拒绝,因为不是生成模型)、需要引用原文出处的判断(它只给概率不给理由)、比 state 上限(65,536 token)更长的材料(会被 422 拒绝)。

## 三种问题类型

所有问题都挂在同一段背景材料(state)上,一次请求可以混合三种类型:

### 1. noul —— 是/否判断

返回"是"的概率(0~1)。**> 0.5 倾向"是",< 0.5 倾向"否"**,越接近 0 或 1 越确定,0.5 附近表示拿不准。

```json
{"type": "noul", "text": "提前5天订票符合差旅政策吗?"}
```
```json
{"q1": {"type": "noul", "noul": 0.4019}}
```

`instructions` / `criteria` 可选,用来补充判定标准(如 `criteria.true`: "符合", `criteria.false`: "违反")。

**读数口径建议**:产品上不要把 0.4019 读成"40% 概率符合",它是模型的倾向度。建议按区间呈现:≥0.8 "符合"、0.6~0.8 "倾向符合"、0.4~0.6 "不确定,转人工"、0.2~0.4 "倾向不符合"、<0.2 "不符合"。区间阈值应在自己业务数据上标定(见"怎么用置信度")。

### 2. choice —— 多选一

`criteria` 是选项字典,返回:选中的选项 `choice`、完整概率分布 `probabilities`、置信度 `confidence`(0~1)。

```json
{"type": "choice", "text": "这个工单属于哪个类别?", "criteria": {"bug": "功能故障", "billing": "费用争议", "other": "其他"}}
```
```json
{"q1": {"type": "choice", "choice": "billing", "confidence": 0.62,
        "probabilities": {"bug": 0.11, "billing": 0.73, "other": 0.16}}}
```

**设计建议**:选项之间要互斥且覆盖全集;拿不准时显式加一个 `other`(其他)选项兜底,否则模型会被迫在都不贴切的选项里硬选;选项描述写清楚判据,不只写类别名。

### 3. score —— 分级评分

`criteria` 是**按等级顺序**排列的描述数组,返回期望等级 `score`(如 2.4 代表"介于 2 级和 3 级之间")、每个等级的概率、置信度。

```json
{"type": "score", "text": "评估这条回复的语气友好程度", "criteria": ["很敌对", "冷淡", "中性", "友好", "非常热情"]}
```
```json
{"q1": {"type": "score", "score": 2.83, "confidence": 0.41,
        "legend": {"0": "很敌对", "1": "冷淡", "2": "中性", "3": "友好", "4": "非常热情"},
        "probabilities": {"0": 0.02, "1": 0.18, "2": 0.49, "3": 0.26, "4": 0.05}}}
```

**设计建议**:等级 3~7 级最合适;每级描述要给出可区分的判据(如"出现辱骂词汇" vs "语气生硬但无辱骂"),只写"好/中/差"会让相邻等级难以区分、置信度偏低。

## 怎么用置信度(confidence)

- **choice / score** 返回 0~1 的 confidence:0 = 完全均匀分布(拿不准),1 = 概率全部集中在一个选项(非常确定)。
- **noul** 没有 confidence 字段,`noul` 值离 0.5 的距离就是它的确定程度。
- **建议的产品策略**:confidence 高于阈值(如 0.4)直接自动化;低于阈值转人工复核。阈值应该在你们自己的业务数据上标定,不要照抄。

### 阈值标定方法(接入必做)

1. 从业务历史数据取 **200~500 条已有人工结论的样本**,覆盖各类别/各难度,别只用典型样本。
2. 用拟上线的 state 结构和问题逐条跑 Kev,记录每条的输出概率/confidence。
3. 以人工结论为真值,画"阈值 → 自动化覆盖率/准确率"曲线:
   - 阈值调高 → 自动放行的样本更少,但放行得更准;
   - 阈值调低 → 覆盖率更高,错误放行更多。
4. 按业务可接受的错误率选阈值。常见落地:**高置信自动执行、中间区间人工复核、低置信直接打回**。例如 choice 题 confidence ≥ 0.6 自动分类,0.3~0.6 人工抽检,< 0.3 转人工。
5. 上线后每周抽检自动化结果的 1%~5%,发现漂移就重新标定。

## 接入流程(从想用到上线)

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1. 场景定义 | 明确判断目标,拆成 noul/choice/score 题 | 问题清单(题 ID、类型、选项/等级、判据) |
| 2. state 设计 | 确定材料里放哪些字段、字段名怎么起 | state JSON 模板(见下节) |
| 3. 小样本试跑 | 拿 20~50 条真实样本调问题和判据措辞 | 稳定的问题措辞 |
| 4. 阈值标定 | 按上节方法定自动化阈值 | 各题阈值表 |
| 5. 联调接入 | 按《接口文档》对接,带上错误处理与重试 | 可调用的业务接口 |
| 6. 灰度上线 | 先并行跑(机器判断+人工判断),对比一致率 | 一致率报告 |
| 7. 正式运行 | 转全自动+人工抽检,监控置信度分布 | 抽检与漂移监控机制 |

### state 组织最佳实践

- **字段名会出现在模型面前**,用有业务含义的 key:`{"差旅政策": "...", "本次申请": "..."}` 好于 `{"a": "...", "b": "..."}`。
- **判定需要的所有事实都要放进 state**,别指望模型外部知识——它不知道你公司今年新出的补充规定,除非你放进去。
- **关键信息放前面或单独成字段**:长材料中埋藏的关键条款,建议抽出来作为独立字段(如 `"重点条款": "..."`)。
- **保持结构稳定**:同一业务的 state 字段名和顺序固定下来,既利于模型表现稳定,也利于命中前缀缓存(同一份材料反复提问时显著更快)。
- **控制长度**:材料 ≤ 16,384 token 可命中前缀缓存;上限 65,536 token(约 4~8 万汉字),超长直接 422。中文 1 汉字 ≈ 0.6 token,可按"字符数 × 0.6"粗估。

## 容量与性能(本部署实测)

| 指标 | 值 |
|---|---|
| 单请求延迟(短材料,单题,缓存命中) | **~120–230 ms**(随并发升高,详见《压测报告》) |
| 一次请求的问题数 | 不限(一次编码全部算完,合并请求远优于拆分) |
| state 长度上限 | 65,536 token(约 4~8 万汉字) |
| 前缀缓存上限 | 16,384 token(超过则不缓存,每次重算) |
| 单题上限 | 8,192 token |
| 选项数上限 | 255 |
| 显存占用 | 空闲 16.9 GiB,满载可达 32 GiB(V100-32G 独占) |
| 吞吐参考 | 短材料单题 ~53 QPS;新材料首次处理(5k token)~0.28 份/s |
| 并发 | 服务内部自动组批;**新材料批量预处理有硬上限**,排期前必读《压测报告》 |

## 使用须知(重要)

1. **没有文本生成**:Kev 的输出只有概率和判断,不会有"因为……所以……"。需要解释就自己写规则引擎,把 state 组织得更结构化。
2. **概率不是概率论意义上的保证**:温度校准过的模型,ECE(期望校准误差)在训练分布上 ~0.02,但跨领域不保证。上自动流程前,先在你们自己的样本上抽检校准。
3. **中文可用但以英文语料训练为主**:判断类任务(政策符合性、分类、评分)中文表现良好;极专业的中文术语建议在 `criteria` 里给出明确定义。
4. **材料越相关越好**:把判定需要的所有事实放进 state,别指望模型外部知识。长材料中埋藏的关键信息建议放在 state 前部或明确标注。
5. **服务无人值守**:容器 `restart: unless-stopped`,宕机自愈;但宿主机或 GPU 故障需要人工介入。服务为**单点部署、内网无鉴权**,不要把涉敏材料用于未授权范围,也不要把端口暴露到内网之外。

## 常见问题(FAQ)

**Q: 返回的 confidence 很低,是服务坏了吗?**
A: 大概率不是问题措辞或材料的问题:选项/等级描述太笼统、选项间有重叠、材料里缺判定所需事实,都会拉低置信度。先按"阈值标定方法"第 3 步排查,再怀疑服务。

**Q: 同一道题两次跑结果略有不同?**
A: 本部署为 fp32 精确路径,同输入同输出;若结果不同,检查请求是否真的逐字节一致(state 字段顺序、空格、标点不同都会改变输入)。

**Q: 一次请求最多能挂多少题?**
A: 协议不限题数,单题上限 8,192 token。实测一次挂几十题代价很小;但不建议无节制堆题——每题都有独立小开销,且一次请求失败要整体重试。经验值:单请求 5~50 题。

**Q: 材料超过 65,536 token 怎么办?**
A: 服务端直接 422 拒绝,不会截断(本部署未开截断)。需要在业务侧先做材料切分/摘要,或只放与判定相关的章节。

**Q: 能不能判断"材料里没有提到的事"?**
A: 不能,这是设计使然。模型只基于 state 内容判断;材料缺失时它会按倾向性猜,置信度通常偏低——这也是"低置信转人工"策略重要的原因。

**Q: 结果错了找谁?**
A: 先记录响应头 `x-typesafe-request-id` 和完整请求体,按《接口文档》排障章节自查;确认是服务端问题再联系部署方。

## 快速上手

curl 版:

```bash
curl -X POST http://10.94.1.8:8009/v1/systemone \
  -H 'Content-Type: application/json' \
  -d '{
    "state": {"政策": "经济舱需提前7天预订,住宿每晚400元以内"},
    "questions": {
      "合规": {"type": "noul", "text": "提前5天订经济舱符合政策吗?"},
      "等级": {"type": "score", "text": "该行为违规程度", "criteria": ["无违规", "轻微", "严重"]}
    }
  }'
```

返回:

```json
{"model":"kev-latest",
 "answers":{"合规":{"type":"noul","noul":0.4019},
            "等级":{"type":"score","score":1.9,...}},
 "usage":{"input_tokens":44,"output_tokens":71},
 "latency_ms":232.0}
```
