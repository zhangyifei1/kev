# Kev-4B 接口文档

> Base URL:`http://10.94.1.8:8009`(内网,HTTP,无鉴权)
> 协议兼容 TypeSafe System One;任何 TypeSafe SDK 把 `base_url` 指到这里即可直接使用。
> 读者:接入方开发。概念与场景见《产品说明书》,运维见《技术文档》。

## 端点总览

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/systemone` | **主端点**:一批问题挂一段材料,一次返回全部判断 |
| GET | `/v1/models` | 模型卡片:版本、精度、温度、缓存与批次统计 |
| POST | `/v1/systemone/permute` | 调试端点:同一 choice 题在 n 种选项顺序下重复判定 |
| POST | `/v1/systemone/separate` | 调试端点:每题独立成请求分别判定(与主端点对比) |

通用约定:

- 请求/响应均为 `application/json`,UTF-8。
- 每个响应带 `x-typesafe-request-id` 头(回显请求传入值,否则自动生成),排查问题时报这个 ID。
- 每个响应带 `server-timing` 头(服务端耗时分解)。
- 概率统一四舍五入到 4 位小数。
- CORS 全开(任意来源/方法/头)。
- 本部署未设置 `KEV_API_KEY`,不鉴权;若部署方日后设置,需在 `/v1/*` 请求加 `Authorization: Bearer <key>`,否则 401。

## 限制速查表

| 限制项 | 值 | 超限行为 |
|---|---|---|
| state 总长度 | 65,536 token | 422,`detail` 含实际 token 数 |
| 单题长度(text+instructions+criteria 压平后) | 8,192 token | 422 |
| choice/score 选项数 | 1~255 | 422 |
| 一次请求题数 | 协议不限 | 建议 5~50 题(见"多题计价与成本") |
| 前缀缓存可缓存的 state 上限 | 16,384 token | 不报错,只是不缓存、每次重算 |
| permute 的 n_perm | 1~64 | 422 |
| 请求超时 | 服务端无硬超时 | 客户端建议:短材料 30s,长材料冷启动 120s |

中文 token 粗估:**1 汉字 ≈ 0.6 token**(即 token ≈ 字符数 × 0.6)。英文单词约 0.75 token/词。

## POST /v1/systemone

### 请求体

```jsonc
{
  "state": <JSONContent>,          // 必填。背景材料,任意 JSON(字符串/对象/数组),会被压平成纯文本给模型
  "model": "kev-latest",           // 可选,默认 "kev-latest";"jev-latest" 也可
  "questions": {                   // 必填。问题字典:key 是你起的问题 ID,值见下
    "<问题ID>": <Question>, ...
  }
}
```

`state` 的压平规则(`render`):

- 字符串/数字/布尔 → 原样;
- 对象 → 每个 key 变成标签行,如 `{"政策": "..."}` → `政策:\n...`;
- 数组 → 缩进的 `- ` 列表;
- 嵌套递归缩进。**字段名会出现在模型面前**,所以用有业务含义的 key。

### Question 三种类型

**noul(是/否)**

```jsonc
{
  "type": "noul",
  "text": "问题文本(和 choice/score 的 text 一样是可选的说明)",
  "instructions": <JSONContent>,          // 可选,给模型的补充指令
  "criteria": {"false": "...", "true": "..."}  // 可选,两侧的含义说明
}
```

**choice(多选一)**

```jsonc
{
  "type": "choice",
  "criteria": {"<选项名>": <描述>, ...}   // 必填,1~255 个;描述可为 null
}
```

**score(分级评分)**

```jsonc
{
  "type": "score",
  "criteria": ["等级0描述", "等级1描述", ...]  // 必填,1~255 个,按等级顺序排列
}
```

### 响应体

```jsonc
{
  "model": "kev-latest",
  "answers": {
    "<问题ID>": {
      // noul:
      {"type": "noul", "noul": 0.4019},                              // p(是)
      // choice:
      {"type": "choice", "choice": "billing", "confidence": 0.62,   // 选项名, 置信度
       "probabilities": {"bug": 0.11, "billing": 0.73, "other": 0.16}},
      // score:
      {"type": "score", "score": 2.83, "confidence": 0.41,          // 期望等级(浮点), 置信度
       "legend": {"0": "很敌对", ...}, "probabilities": {"0": 0.02, ...}}
    }
  },
  "usage": {"input_tokens": 44, "output_tokens": 71},
  "latency_ms": 232.0
}
```

- `confidence`(choice)= `(p_max − 1/K) / (1 − 1/K)`,均匀分布 0,全押一个选项 1(与 TypeSafe 参考实现同公式)。
- `confidence`(score)= `max(0, 1 − E|level − mode| / D)`,D 为均匀分布围绕均值的平均绝对偏差。
- `usage.input_tokens`:材料+问题压平后的 token 数(计费口径);`output_tokens`:答案序列化的 token 数,不是生成量(Kev 不生成文本)。
- 若部署时开了 `KEV_TRUNCATE_STATES=1`,超长 state 会被截断且响应多出 `"truncated": true` 与 `usage.state_tokens / state_tokens_used`;**本部署未开启**,超长直接 422。

### 错误码

| 状态码 | 场景 | 客户端处理建议 |
|---|---|---|
| 200 | 成功 | — |
| 401 | 未设置鉴权时不会出现 | `KEV_API_KEY` 设置后 key 缺失/错误;联系部署方确认 |
| 422 | 请求形状错误 / 超长 | **不要重试**,修正请求:FastAPI 校验错误有 `detail` 数组;state 超 65,536 token 或单题超 8,192 token 时 `detail` 为一句人话(含实际 token 数和上限),此时该请求未被计费处理 |
| 500 | 服务端内部错误(如极端显存压力 OOM) | 指数退避重试 1~2 次;持续 500 联系部署方查 `docker logs` |
| 503 | 服务正在停止 | 重启/发布窗口期,等 1~2 分钟重试 |
| 连接拒绝/超时 | 容器或宿主机故障 | 先查服务状态(见"排障自查"),不要无限重试打满队列 |

422 超长示例:

```json
{"detail": "state is 71,234 tokens; the limit is 65,536 ... (or start the server with KEV_TRUNCATE_STATES=1 ...)"}
```

### 多题计价与成本

一次请求的耗时 ≈ 状态编码(大头,只算一次)+ 每题一小步。**把 50 个问题塞进同一请求远快于发 50 个请求**。相同 state 反复提问会命中前缀缓存(见 /v1/models 的 `prefix_cache`),延迟更低;本部署状态缓存上限 16,384 token,超长状态不缓存。

**两个反模式**:

1. **一题一请求**:每请求都要重付状态编码,题多时总耗时成倍放大(除非题挂在不同材料上)。
2. **state 微小抖动**:同一材料每次请求拼 JSON 时字段顺序/空白不同,会成为"新 state"导致缓存 miss。固定序列化方式(如 Python `json.dumps(..., sort_keys=True, ensure_ascii=False)`)。

Python(标准库,最小可用):

```python
import json, urllib.request

def kev(state, questions, base="http://10.94.1.8:8009"):
    body = json.dumps({"state": state, "questions": questions}).encode()
    req = urllib.request.Request(f"{base}/v1/systemone", body,
                                 {"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=300) as r:
        return json.load(r)["answers"]

ans = kev(
    state={"政策": "经济舱需提前7天预订;住宿每晚400元以内"},
    questions={"合规": {"type": "noul", "text": "提前5天订经济舱符合政策吗?"}},
)
print(ans["合规"]["noul"])        # 0.4019 -> 倾向"否"
```

### 生产级 Python 客户端(推荐直接抄)

带连接复用、超时分级、退避重试、request-id 透传:

```python
import json, time, uuid, urllib.request, urllib.error

BASE = "http://10.94.1.8:8009"

class KevError(Exception):
    def __init__(self, status, detail, req_id):
        super().__init__(f"kev {status}: {detail} (request_id={req_id})")
        self.status, self.detail, self.req_id = status, detail, req_id

def kev_call(state, questions, timeout=120, retries=2, req_id=None):
    """返回 answers 字典。422 不重试,5xx/网络错误指数退避重试。"""
    req_id = req_id or str(uuid.uuid4())
    body = json.dumps({"state": state, "questions": questions},
                      sort_keys=True, ensure_ascii=False).encode()  # sort_keys: 稳定序列化,利于前缀缓存命中
    last = None
    for attempt in range(retries + 1):
        req = urllib.request.Request(
            f"{BASE}/v1/systemone", body,
            {"Content-Type": "application/json", "x-typesafe-request-id": req_id})
        try:
            with urllib.request.urlopen(req, timeout=timeout) as r:
                return json.load(r)["answers"]
        except urllib.error.HTTPError as e:
            detail = e.read().decode("utf-8", "replace")[:500]
            if e.code == 422:                       # 请求本身有问题,重试无意义
                raise KevError(422, detail, req_id)
            last = KevError(e.code, detail, req_id)
        except (urllib.error.URLError, TimeoutError) as e:
            last = KevError(-1, str(e), req_id)
        if attempt < retries:
            time.sleep(2 ** attempt)                # 1s, 2s ...
    raise last
```

使用要点:

- **超时按材料长度设**:短材料 30s 足够;5k token 新材料首次处理约 3.6s、10k 约 7.6s,批量场景建议 120s(排队时会线性放大,见《压测报告》)。
- **批量任务加客户端侧节流**:新材料首处理吞吐是服务端硬上限(5k token ≈ 0.28 份/s),并发开得再高也只是排队,还会把显存推向 OOM。建议新材料批处理并发 ≤ 4。
- **request-id 贯穿日志**:出问题时把 `req_id` 发给部署方,可在服务端日志中直接定位。

TypeSafe SDK:

```python
from typesafe import TypeSafeClient

client = TypeSafeClient(api_key="local", base_url="http://10.94.1.8:8009", model="kev-latest")
resp = client.systemone(state=..., questions=...)
```

## GET /v1/models

返回所有接受的模型名(目前 `kev-latest`、`jev-latest`)的卡片:

```jsonc
{"models": [{
  "name": "kev-latest",
  "description": "Kev pointer head on Qwen/Qwen3.5-4B-Base, serving jaredpalmer/kev-4b at temperature 2.41",
  "release_date": "2026-10-01",
  "run": "jaredpalmer/kev-4b",            // 底层 checkpoint
  "base": "Qwen/Qwen3.5-4B-Base",
  "lora": 16, "device": "cuda", "backend": "torch", "dtype": "float32",
  "temperature": 2.41,                     // 输出校准温度,内置于 checkpoint
  "max_state_tokens": 65536, "truncate_states": false,
  "cuda_graphs": null,                     // V100 部署为 null(未启用)
  "prefix_cache": {"cached_states": 0, "hits": 0, "misses": 0, ...},
  "batches": {"count": 0, "requests": 0, "queued": 0}
}]}
```

健康检查/监控直接轮询本端点即可(compose 的 healthcheck 也是打它)。

**接入方可以怎么用这些字段**:

| 字段 | 用法 |
|---|---|
| `batches.queued` | > 20 说明服务端排队积压,客户端应放慢发送速率,否则延迟会线性恶化 |
| `prefix_cache.hits / misses` | 命中率低而你预期"同材料反复提问"时,检查 state 序列化是否稳定 |
| `dtype / cuda_graphs` | 跨部署对比数值时确认精度路径(本部署 fp32,与官方 bf16 有 ~1e-3 级差异) |

## POST /v1/systemone/permute

选项顺序鲁棒性调试:把请求中**一道 choice 题**在 n 种选项排列下重复判定(第一种为原始顺序,其余按 seed 洗牌)。

```jsonc
// 请求
{"request": <完整 SystemOneRequest>, "question": "<题ID>", "n_perm": 6, "seed": 0}
// n_perm: 1~64,默认 6;每种顺序是一次完整前向
```

```jsonc
// 响应
{"runs": [{"order": ["bug","billing","other"], "probabilities": {...}, "choice": "billing", "latency_ms": 210.0}, ...],
 "argmax_stable": true,        // 所有顺序选出的选项是否一致
 "spread": {"bug": 0.01, "billing": 0.04, "other": 0.03}}  // 每个选项概率的 max-min
```

`argmax_stable: false` 或 spread 大,说明该判断对选项顺序敏感,建议人工复核或调整选项描述。

**什么时候用**:新场景上线前,对关键 choice 题跑一次 permute;`argmax_stable: false` 的题说明选项边界模糊,要么改选项描述,要么该产品位转人工。

## POST /v1/systemone/separate

把同一请求的每道题拆成独立请求分别判定(N 次前向),返回与主端点同构的合并结果。用于对比打包判定与独立判定的差异;生产上没有理由用它(更慢)。

**什么时候用**:怀疑"题目之间互相干扰"(打包结果和单独问不一致)时做对照实验;两者差异显著时,把干扰大的题拆到不同请求。

## 排障自查(接入方)

| 现象 | 先查什么 | 大概率原因 |
|---|---|---|
| 连接被拒/超时 | 浏览器或 curl 打 `GET /v1/models` | 服务宕机或重启中(503 窗口 1~2 分钟);持续不可达找部署方 |
| 422 `detail` 提 token 数 | 用"字符数 × 0.6"估算 state 长度 | 材料超 65,536 token;切分或精简材料 |
| 422 `detail` 是字段校验数组 | 对照本文 Question 结构逐字段查 | type 拼写、criteria 缺失、选项数 0 或 >255 |
| 全部请求变慢 | 轮询 `/v1/models` 看 `batches.queued` | 上游有大批量任务在跑;排队,稍后恢复 |
| 结果和预期不符 | 拿同一请求打 `/v1/systemone/separate` 对比;对 choice 题打 permute | 题间干扰 / 选项顺序敏感 / 材料里缺事实 |
| 间歇 500 | 记录 `x-typesafe-request-id` 报部署方 | 极端并发下显存压力,需服务端介入 |

## 部署特定的行为差异

相对官方文档,本 V100 部署的差异只有性能与精度路径,接口形状完全一致:

| 项 | 本部署 | 官方默认 |
|---|---|---|
| 精度 | fp32(V100 无 bf16 硬件支持) | bf16 |
| fused 内核 / CUDA graphs | 关闭(Volta 跑不了 fla Triton 内核) | 开启 |
| 延迟 | ~120–230 ms(短材料单题,随并发升高) | 数十 ms |
| 状态前缀缓存上限 | 16,384 token(超长状态不缓存,每次重算) | 65,536 |
| 温度截断(`KEV_TRUNCATE_STATES`) | 关闭:超长 state 返回 422 | 同 |
