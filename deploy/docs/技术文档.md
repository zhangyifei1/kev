# Kev-4B 技术文档(V100 内网部署)

> 范围:本文描述这台 V100 服务器上这套部署的架构、构建方式、运维操作和已知约束。模型本身的原理见上游仓库 README 与 model card,不在此展开。
> 读者:部署方运维、值班排障人员。接入方请先看《接口文档》。

## 1. 部署对象

- **模型**:`jaredpalmer/kev-4b`——4B 参数 LoRA + pointer head,底座 `Qwen/Qwen3.5-4B-Base`。
- **硬件**:Tesla V100-SXM2-32GB(1 号卡,Volta 架构 sm_70)。
- **形态**:Docker 镜像 `kev-4b:latest`(11.7GB)+ docker-compose,容器名 `kev-4b`,暴露 `8009`。
- **目录**:宿主机 `/home/ubuntu/zhangyifei/kev-docker/`(代码与部署配置),`deploy/` 内含全部部署文件。
- **配置仓库**:上游 Kev 仓库 `deploy/` 目录(只存于公司内网 git,**不推送公开仓库**——含内网地址与镜像源)。

## 2. 部署架构

### 2.1 架构图

```
                       内网客户端(业务系统 / 压测机 / 运维)
                                │  HTTP :8009
                                ▼
┌───────────────────────── 宿主机 (V100 服务器) ─────────────────────────┐
│                                                                       │
│   docker-compose ──► 容器 kev-4b (restart: unless-stopped)            │
│                        │                                              │
│                        ├─ entrypoint.sh: hf-mirror 预下载模型          │
│                        │        │ (首次/模型变更时)                    │
│                        │        ▼                                     │
│                        ├─ python -m kev.serve --port 8009             │
│                        │      单模型线程:请求排队 → 组批 → GPU 前向     │
│                        │      前缀缓存(≤16384 token 的 state)         │
│                        │                                              │
│   volume hf-cache ─────┤ /data/hf (模型缓存:底座 ~8GB + 适配器)        │
│                        │                                              │
│   nvidia-container-runtime ──► 注入 GPU 1 号卡 + 宿主驱动              │
│                        │                                              │
│   healthcheck: python urllib 打 /v1/models, 30s/次, start_period 30m  │
└───────────────────────────────────────────────────────────────────────┘
```

### 2.2 数据流(一次请求的生命周期)

1. 客户端 POST `/v1/systemone`(state + questions)。
2. FastAPI 校验请求形状;超长 state(>65,536 token)直接 422,不进入队列。
3. 请求进入**单模型线程队列**;相同 state 且 ≤16,384 token 时命中前缀缓存,跳过状态编码。
4. 未命中缓存:state 全量 prefill(GPU 串行,4.8k token ≈ 3.6s,9.5k ≈ 7.6s——这是新材料吞吐的硬上限)。
5. 命中缓存或 prefill 完成后:每题一次小的分支前向,算出概率分布。
6. 统一序列化返回(概率 4 位小数),带 `x-typesafe-request-id` 与 `server-timing` 头。

**运维要点推论**:队列是串行的,`batches.queued` 积压时长材料的队尾延迟 = 队头各请求 prefill 耗时之和。这就是"并发再高吞吐不变"的原因(见《压测报告》)。

### 2.3 V100(Volta)的硬约束

| 约束 | 后果 | 处理 |
|---|---|---|
| 无 bf16 硬件支持 | 不能跑官方默认的 bf16 服务路径 | `KEV_DTYPE=fp32` |
| 无 TF32 | fp32 matmul 无加速路径 | 接受,延迟 ~120–230ms/短请求 |
| 跑不了 fla 的 Triton 内核 | fused DeltaNet 内核不可用 | `KEV_FUSED=0`,eager 路径 |
| sm_70 | CUDA 图/部分新内核特性不可用 | `KEV_CUDA_GRAPHS=0`,`/v1/models` 里为 `null` |

fp32 下权重约 16.8GB,调优后空闲稳态 16.9 GiB,极限满载 32 GiB(压测细节见《压测报告》)。

### 2.4 内网链路的硬约束

这台机器**出网受限**:GitHub、HuggingFace、debian apt 源均不可达;PyPI 国内镜像可达但动态限速,uv(Rust rustls TLS 指纹)被限到 KB/s 级。由此产生的构建决策:

1. **完全离线构建**:依赖在本机(开发者 PC)用 `pip download` 跨平台下载成 93 个 Linux wheel(3.8GB),tar 传输到服务器,Dockerfile 里 `pip install --no-index --find-links /wheels`。源码与 lockfile(`uv.lock`)一起进构建上下文,版本与上游锁死。
2. **不走 apt**:`python:3.13-slim` 自带 ca-certificates;healthcheck 用 python 标准库而不是 curl。基础镜像只是运行环境——CUDA 用户态库(nvidia-*-cu12 的 wheel)随 torch 依赖装进容器,GPU 由宿主机的 nvidia-container-runtime 注入。
3. **模型走 hf-mirror**:`HF_ENDPOINT=https://hf-mirror.com`;新 `huggingface_hub` 默认的 Xet 协议 hf-mirror 不支持(401),必须 `HF_HUB_DISABLE_XET=1` 回退普通 HTTP。模型缓存在 named volume,重建容器不重下。

### 2.5 GPU 容器原理(常见误解澄清)

基础镜像 `python:3.13-slim` 是"CPU 镜像"不影响用 GPU:**CUDA 内核驱动来自宿主机**(nvidia-container-runtime 把 `/dev/nvidia*` 与驱动库挂进容器),用户态 CUDA 运行时来自 torch 的 pip 依赖。因此基础镜像不需要装 CUDA,只需要 pip 依赖里有 `nvidia-cublas-cu12` 等 wheel(已包含)。

```

    ├── entrypoint.sh             # 启动前 hf-mirror 预下载模型 -> exec python -m kev.serve
    ├── deploy-all.sh             # 一键构建+启动(docker build --network=host;日志 deploy/build.log、deploy.log)
    ├── requirements.txt          # uv export 生成的精确依赖清单(120 包)
    ├── docs/                     # 本文档、产品说明书、接口文档、压测报告
    ├── bench/                    # 压测脚本与结果(load_test.py, results/results.json)
    └── wheels/                   # 93 个预下载 Linux wheel(3.8GB)——构建物料,删除则需重新下载
```

关键 compose 配置:

| 项 | 值 | 作用 |
|---|---|---|
| `device_ids: ["1"]` | 固定 1 号卡 | 不占其他卡 |
| `KEV_DTYPE: fp32` | fp32 权重 | Volta 必需 |
| `KEV_FUSED: "0"` | eager 路径 | Volta 无 fused 内核 |
| `KEV_CUDA_GRAPHS: "0"` | 关 CUDA 图 | 私有池占 3GB,fp32 eager 收益小,为长状态腾显存 |
| `PYTORCH_CUDA_ALLOC_CONF: expandable_segments:True` | 可扩展段分配器 | 减少碎片,峰值能撑满全卡 |
| `KEV_PREFIX_MAX_TOKENS: "16384"` | 前缀缓存上限 | 控制显存(fp32 KV 大);超长状态不缓存 |
| `HF_HUB_DISABLE_XET: "1"` | 禁 Xet 下载 | hf-mirror 不支持 |
| `shm_size: 2g` | 共享内存 | torch 组批 IPC 需要 |
| `restart: unless-stopped` | 自愈 | 宕机自动拉起 |
| healthcheck | python urllib 打 `/v1/models`,`start_period: 30m` | 首启含模型下载,窗口放宽 |

## 4. 运维手册

### 4.1 常用命令(服务器上)

```bash
cd /home/ubuntu/zhangyifei/kev-docker/deploy

docker compose ps                 # 状态(health: healthy 为正常)
docker logs -f kev-4b             # 日志
docker compose restart            # 重启(模型有缓存,1-2 分钟恢复服务)
docker compose down               # 停止并移除容器(模型缓存 volume 保留)
docker compose up -d              # 重新启动
docker compose up -d --force-recreate  # 改了 compose 配置后应用
```

### 4.2 巡检清单

**每日(可脚本化)**:

```bash
# 1. 健康状态
docker inspect kev-4b --format '{{.State.Health.Status}}'   # 期望 healthy
# 2. 显存(1 号卡):空闲 ~16.9GiB 正常;≥28GiB 预警
nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv
# 3. 队列与缓存
curl -s http://127.0.0.1:8009/v1/models | python -m json.tool | grep -A5 batches
```

**每周**:

- `docker logs kev-4b --since 168h 2>&1 | grep -iE 'error|oom|retry' | tail -50` —— 排查错误与 OOM 重试记录。
- `df -h` 检查磁盘(模型 volume ~9GB、镜像 11.7GB、日志增长)。
- 确认 wheels 备份存在(见 4.6)。

### 4.3 监控告警建议

| 指标 | 采集方式 | 告警线 | 处置 |
|---|---|---|---|
| 健康状态 | `docker inspect ... Health.Status` | ≠ healthy 持续 2 分钟 | 按 4.4 runbook A |
| 1 号卡显存 | `nvidia-smi` | ≥ 28 GiB | 按 4.4 runbook B |
| `batches.queued` | `/v1/models` | > 20 持续 5 分钟 | 通知上游限流;排查批量任务 |
| HTTP 5xx 率 | 接入方日志 | 任一时间窗 > 1% | 查 `docker logs` OOM 记录 |
| GPU 利用率 | `nvidia-smi` | 持续 100% 且 queued 增长 | 正常满载;评估扩容/限流 |

### 4.4 故障处置 Runbook

**A. 服务不可达 / healthcheck 失败**

1. `docker compose ps` 看容器是否在跑、`docker logs --tail 100 kev-4b` 看最后日志。
2. 容器退出:看日志定位(OOM 见 B;模型下载失败见 D;其他异常贴日志上报)。
3. 容器在跑但无响应:大概率在 prefill 长队列或被极端请求卡死,`docker compose restart`。
4. restart 后 `docker compose ps` 等 healthy(模型已缓存,1~2 分钟)。

**B. OOM(torch.OutOfMemoryError,HTTP 500)**

1. `docker logs kev-4b 2>&1 | grep -i oom | tail` 确认。
2. 确认当前显存:`nvidia-smi`。调优后正常不会 OOM;若复现,先 `docker compose restart` 回收显存到 16.9 GiB 稳态。
3. 通知上游:并发长状态(≥4k token)请求不要超过 8 个(容量公式见《压测报告》第四节)。
4. 频繁复现:考虑下调 `KEV_PREFIX_MAX_TOKENS`(如 8192)或限客户端并发。

**C. 显存缓慢爬升**

PyTorch 分配器只借不还属预期;压测/高峰后执行 `docker compose restart` 回到稳态。不影响服务时可不处理。

**D. 模型下载失败(启动阶段)**

1. 日志里 `hf download` 报错:确认 `HF_ENDPOINT=https://hf-mirror.com` 与 `HF_HUB_DISABLE_XET=1` 都在 compose 里。
2. 手动试下:`docker exec -it kev-4b hf download jaredpalmer/kev-4b`(容器重建中则在宿主用同样 env 试)。
3. hf-mirror 也不可达时:从备份机器 `docker save kev-4b | ssh ... docker load` 搬镜像,或把已有 `hf-cache` volume 整体拷贝过去。

**E. 端口不通但容器 healthy**

查宿主机防火墙/安全组是否放行 8009;`ss -tlnp | grep 8009` 确认监听在 `0.0.0.0`。

### 4.5 完整重建(改代码/Dockerfile 后)

```bash
cd /home/ubuntu/zhangyifei/kev-docker/deploy
./deploy-all.sh                   # build --network=host + compose up;日志在 build.log / deploy.log
```

构建走 `--network=host` 是有意为之:buildkit 默认构建容器网络会命中劣质 CDN 节点导致下载卡死。

### 4.6 数据与持久化

- **模型缓存**:named volume `hf-cache` 挂在 `/data/hf`(底座 8GB + 适配器)。删 volume 会触发重新下载(几分钟,可接受但不必要)。
- **容器本身无状态**:重建容器不丢任何业务数据(服务本就不持久化请求)。
- **关键备份**:
  - `tar -cf kev-wheels.tar deploy/wheels`(3.8GB,构建命脉,存到别的机器);
  - `deploy/` 整个目录(配置 + 文档 + 压测脚本)纳入内网 git;
  - `hf-cache` volume 可不备(可从 hf-mirror 重下),但备份一次可省去新环境首启等待。
- **迁移到新机器**:新机装 docker + nvidia-container-toolkit → 拷贝整个 `kev-docker/` 目录 → `./deploy-all.sh` → 首启自动从 hf-mirror 下模型。如新机器出网同样受限,可 `docker save kev-4b | ssh ... docker load` 直接搬镜像(11.7GB)。

### 4.7 监控要点速查

- `docker inspect kev-4b --format '{{.State.Health.Status}}'` → `healthy`
- `nvidia-smi` 1 卡显存:空闲 ~16.9GiB 正常;若逼近 32GiB 需要查 OOM(`docker logs` 会有重试记录)
- `/v1/models` 的 `prefix_cache.hits/misses`、`batches.queued` 可看负载

### 4.8 升级模型版本

改 compose 的 `KEV_MODEL`(与必要的 `KEV_BASE`)→ `docker compose up -d --force-recreate` → entrypoint 自动下载新模型。注意:更大模型需先核对 fp32 显存(参数量 × 4 字节 + ~6GB 工作集;32GB 卡上限约 6B)。

### 4.9 变更管理(改配置的标准动作)

1. 改 compose/Dockerfile 前,先在内网 git 提交当前可用版本。
2. 变更窗口选在业务低峰;提前通知接入方(重启有 1~2 分钟 503 窗口)。
3. 应用变更:`docker compose up -d --force-recreate`(仅 env)或 `./deploy-all.sh`(镜像层)。
4. 验证三件套:healthcheck healthy → `curl /v1/models` 返回正常 → 发一条真实请求确认 200。
5. 验证失败回滚:git 还原配置 → 重新 `--force-recreate`。

## 5. 构建过程踩过的坑(修复已固化,记录供日后排障)

| 症状 | 根因 | 修复 |
|---|---|---|
| `uv sync` 在容器内卡死 | uv 的 rustls TLS 指纹被链路 QoS 到 KB/s | 整体改离线 wheel 构建 |
| `docker build` 下载卡死但 run 容器很快 | buildkit 构建容器网络命中劣质节点 | `--network=host` |
| `apt-get update` 卡死 | debian 源不可达 | 去掉 apt 层(slim 自带 CA) |
| `pip install -e .` 报 `No matching distribution found for setuptools>=77` | PEP 517 构建隔离环境不继承 `--no-index`/`--find-links` | `--no-build-isolation`(setuptools 已由 requirements 装入主环境) |
| hf 下载 401(CAS/xethub) | hf-mirror 不支持 Xet 协议 | `HF_HUB_DISABLE_XET=1` |
| wheel 包 CRC 损坏 | 传输/下载中途截断(大小碰巧一致) | 传输后逐个 `zipfile.testzip()` 校验;校验过的 wheel 目录勿删 |
| 残留慢速下载进程占着 wheels 目录 | 更换方案时旧进程未清 | `docker kill` + `kill -9` 全链(pip 在容器里跑,`kill` 外层 sh 没用) |
| 压测中 8k+ 请求全部 OOM(HTTP 500) | CUDA Graphs 私有池 3GB + 分配器碎片 | `KEV_CUDA_GRAPHS=0` + `expandable_segments:True`(已固化进 compose) |

## 6. 性能画像

| 场景 | 实测 |
|---|---|
| 短材料(~50 token)单 noul 题,缓存命中 | 124 ms(c=1);满载 53 QPS |
| 短材料 5 题混合 | 261 ms(c=1);~12 请求/s ≈ 58 题/s |
| 相同 state 复用(前缀缓存命中) | 状态编码只付一次,**合并请求优于拆分请求** |
| 新材料首次处理 4.8k token | 3.6 s/份,0.28 份/s 硬上限(单模型线程串行) |
| 新材料首次处理 9.5k token | 7.6 s/份,0.13 份/s |
| 显存 | 空闲 16.9 GiB;极限满载 32 GiB 不崩 |

完整压测矩阵与容量公式见《压测报告》。

上游官方基准(H100/bf16/fused)是本部署的数倍性能,但接口与数值语义一致;跨部署对比概率数值时注意精度路径不同(见下)。

## 7. 数值与可复现性说明

- "fp32-exact":同一内核集下逐位可复现。本部署的内核集 = torch eager fp32,无 Triton/causal-conv1d——与官方 CUDA 部署(bf16/fused)的输出**会有微小数值差异**(约 1e-3 量级,个别临界题可能翻转判断)。跨部署配对读数时要么统一路径,要么接受该差异。
- 温度 2.41 内置于 checkpoint 的 `head.pt`,由 `PointerHead` 在推理模式自动应用;`KEV_TEMPERATURE=1.0` 环境变量可覆盖为原始 logits(仅排障用,勿在生产开启)。

## 8. 已知限制与风险

1. **单点**:单容器单卡,无副本。故障表现为服务不可达,`restart: unless-stopped` 只兜进程级故障,宿主机/GPU 故障需人工。
2. **无鉴权**:当前内网开放。如需鉴权,在 compose 给 `KEV_API_KEY` 设值后 `--force-recreate`,客户端带 `Authorization: Bearer <key>`。
3. **wheels/ 是构建命脉**:删了就构建不出来(重新下载受链路限速制约)。备份建议:`tar -cf kev-wheels.tar deploy/wheels` 存到别的机器。
4. **V100 已停产**:备件与迁移路径(见 4.6 迁移)应提前规划;上游 bf16/fused 路径在更新的卡(H100/H200/B200)上性能更好,迁移时只需删掉 compose 里的 `KEV_DTYPE`/`KEV_FUSED` 两行。
5. **上游同步**:kev/ 源码与上游仓库可能漂移;升级流程 = 覆盖 `kev/` + `pyproject.toml` + `uv.lock` → 重新 `pip download` 生成 wheels(本机执行,脚本参考上游 `deploy/` 文档)→ `deploy-all.sh` 重建。
