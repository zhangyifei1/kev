> 日期:2026-10-14 | 方法:本机(Windows,办公网)直连 `http://10.94.112.8:8009`,Python stdlib 多线程 keep-alive 客户端
> 脚本:`deploy/bench/load_test.py`,原始数据:`deploy/bench/results/results.json` | 所有场景 0 错误(除标注外)

## 一、结论(TL;DR)

| 场景 | 单请求延迟 | 满载吞吐 | 说明 |
|---|---|---|---|
| 短材料单题(~40 tok) | **124 ms** | **53 QPS** | 日常简单判断,可支撑百人级内部使用 |
| 短材料 5 题(~90 tok) | 261 ms | 12 QPS(≈58 题/s) | 一次请求挂多题,吞吐按题数放大 |
| 中材料 5 题(~650 tok) | 225 ms | 10 QPS(≈51 题/s) | 与短材料几乎同量级 |
| 长材料(4.8k tok)重复提问 | 140 ms | 10 QPS | 前缀缓存命中,状态编码只付一次 |
| 超长材料(9.5k tok)重复提问 | 205 ms | 8 QPS | 同上 |
| **长材料首次处理(冷启动)** | **3.6 s** | **0.28 QPS(硬上限)** | 单模型线程串行,并发只排队 |
| 超长材料首次处理(冷启动) | 7.6 s | 0.13 QPS | 同上 |

**三条核心结论:**

1. **同一份材料反复提问是本服务的甜点区**:前缀缓存命中后,9.5k token 的材料单题 205ms、8 QPS;短材料满载 53 QPS。
2. **新材料的首次处理是硬瓶颈**:服务内部单模型线程,GPU 串行编码,吞吐与并发无关(4.8k token 锁死 0.28 QPS,9.5k 锁死 0.13)。批量预审新材料的速率上限 ≈ 每 3.6 秒 1 份(4.8k)。
3. **显存是第一运维指标**:调优前服务进程爬升到 31.65/31.73 GiB,8k 以上请求全部 CUDA OOM(HTTP 500);调优后空闲 16.9 GiB,极限满载撑到 32 GiB 无崩溃(97% GPU 利用率)。

## 四、显存观测与 OOM 事件(本次压测最重要的发现)

### 调优前(初始配置)

- 初始稳态:25.7 GiB(含 CUDA Graphs 私有池 3.01 GiB)
- 压测中持续爬升:**31.65 / 31.73 GiB**(PyTorch 缓存分配器只借不还 + 碎片)
- S4(8k 字符)起**所有请求 HTTP 500**,容器日志:`torch.OutOfMemoryError: Tried to allocate 150.00 MiB. GPU 0 has ... 81.25 MiB free`
- 期间 GPU 采样:180 个样本均值 31.6 GiB、利用率 71%

### 调优动作(compose 环境变量,已固化)

```yaml
KEV_CUDA_GRAPHS: "0"                              # graphs 私有池 3GB,fp32 eager 部署收益小,关
PYTORCH_CUDA_ALLOC_CONF: expandable_segments:True  # 可扩展段:减少碎片,峰值能撑满全卡
```

### 调优后

- 空闲稳态:**16.9 GiB**(释放 ~15 GiB)
- 极限满载(S5C 32 并发冷启动,9.5k token):**32 GiB 撑满不崩**,GPU 利用率 97%
- 压测后服务恢复:短请求 HTTP 200 正常(分配器保留满池但不影响服务);**建议压测/高峰后 `docker compose restart` 回收显存**

### 容量公式(经验)

`显存 ≈ 16.9 GiB(基础) + 0.35 GiB × 并发中的长状态数(每 1k token 约 0.35 GiB fp32 激活)`

32 GB 卡的安全线:**并发长状态(≥4k token)请求不超过 8 个**;超过会触发 OOM 重试兜底,极端时 500。

## 五、性能画像与容量建议

**QPS 参考值(缓存命中,稳态):**

| 业务形态 | 可用吞吐 | 单请求 p50 |
|---|---|---|
| 短材料单题(如单条政策检查) | ~53 QPS,可持续 | 124ms@c1 / 556ms@c32 |
| 短材料批量 5 题 | ~12 请求/s = ~58 题/s | 261ms@c1 |
| 长材料(5k token)反复提问 | ~10 QPS | 140ms@c1 |
| 新材料批量预审(5k/份) | **0.28 份/s ≈ 1,000 份/小时** | 3.6s/份 |
| 新材料批量预审(10k/份) | 0.13 份/s ≈ 470 份/小时 | 7.6s/份 |

**部署建议:**

1. **高吞吐短判断**(工单分类、评论审核):直接上,当前部署可支撑百人级内部系统。
2. **新材料批量预审**:吞吐由 GPU 串行编码决定(与并发无关),按"每小时 ~500-1,000 份(按材料 5k-10k token)"做排期;需要更快就拆分材料或申请 H100(官方 bf16+fused 路径快一个量级)。
3. **监控告警线**:1 卡显存 ≥ 28 GiB 预警(接近 32 GiB 会 500);`/v1/models` 的 `batches.queued` > 20 说明排队积压。
4. **压测工具已入库**:`deploy/bench/load_test.py`(改 HOST 即可复测),报告数据 `deploy/bench/results/results.json`。

## 六、压测执行备注

- S1-S5 的"状态复用"代表"同一份材料反复提问"的真实业务形态;S4C/S5C 代表"每份新材料只处理一次"。两类数据均为真实可达性能,选择参考时先对号入座。
